# Codex subscription protocol

## Version and primary sources

The implementation targets official `@openai/codex` **0.163.0** and the JSON schemas generated by:

```
codex app-server generate-json-schema --experimental --out /tmp/router-codex-schema
```

The generated `v2/ThreadStartParams.json`, `DynamicToolCallParams.json`, `DynamicToolCallResponse.json`, `v2/GetAccountResponse.json`, and `v2/ModelListResponse.json` are the version-specific wire authority. Generation does not authenticate or run inference. The official [app-server documentation](https://learn.chatgpt.com/docs/app-server) documents generating these schemas and warns that dynamic tools require experimental capability opt-in.

## Transport and ownership

App-server stdio is newline-delimited bidirectional JSON-RPC without a `jsonrpc` header. Initialize once with client metadata and `capabilities.experimentalApi: true`, then send `initialized`. Start a thread, start a turn, consume agent-message deltas, and finish on `turn/completed`. See [protocol, initialization, and lifecycle](https://learn.chatgpt.com/docs/app-server#protocol).

Each router conversation owns one live process and thread. A separate lazy admin process handles login, account status, and model discovery. Conversation state lasts only as long as the process: timeout/eviction, cancellation, process failure, logout, and router restart lose the thread. Recently retired keys are rejected rather than silently replayed; the tombstone cache is bounded to the greater of 256 and four times the configured session limit. A request that fails before creating a thread or consuming history does not poison its key, so sign-in permits retrying a previously signed-out request. Active **and queued** reservations prevent eviction. Failed processes retire before releasing their turn gate. Zero idle timeout disables idle expiry. Turns on one key serialize; queued turns honor cancellation without killing another request's process. Cancellation watchers cover pipe writes and are joined before reuse; process-group termination cleans up child processes. The router sends only new history messages, not the entire conversation repeatedly. Changing model/tools/instructions requires a new session.

This is deliberately not durable thread resume. The app-server has [thread resume APIs](https://learn.chatgpt.com/docs/app-server), but restoring an outstanding client RPC after losing its process is not supported by this adapter.

## Native client-owned tools and security

`thread/start.dynamicTools` contains tagged function specifications: `{type:"function",name,description,inputSchema}`. A call is a **server request**, `item/tool/call`, carrying `threadId`, `turnId`, `callId`, `tool`, and arbitrary JSON `arguments`. The router exposes that call without answering the RPC. A matching client tool result answers the original RPC ID with `{contentItems:[{type:"inputText",text:"..."}],success:true}`. Generation then continues in the **same turn**, with no extra `turn/start`. See [dynamic tool calls](https://learn.chatgpt.com/docs/app-server#dynamic-tool-calls-experimental) and generated schemas listed above. Tool output without a matching pending call is an error.

The version-specific `ThreadStartParams.environments` documentation states: **“Empty disables environment access for turns that do not provide a turn override.”** The adapter sends `environments: []` and never adds a turn environment override. This disables the environment-backed host execution/file/network surface, rather than mistaking read-only sandboxing for disabling reads or shell execution. Additional defense-in-depth: `features.shell_tool=false`, `tools.view_image=false`, `web_search="disabled"`, empty MCP configuration, disabled default apps and agents, `sandbox:"read-only"`, `approvalPolicy:"on-request"`, and `approvalsReviewer:"user"`. The shell, image and web settings are documented in the [configuration reference](https://learn.chatgpt.com/docs/config-file/config-reference). An empty MCP map is not independently treated as proof that inherited configuration is absent; the environment selection and rejection of unexpected RPCs are essential boundaries.

Every unexpected server request receives a JSON-RPC error and retires the conversation; no host-action approval, elicitation, token refresh delegation, or user-input request is automatically approved. The adapter never executes a dynamic tool itself. Configured commands are trusted operator configuration, not client request data. Managed Codex policy may reject configuration; those failures must remain visible, not downgraded to a permissive configuration.

Process-level overrides also set `features.hooks=false`, `notify=[]`, `features.multi_agent=false`, and `agents.enabled=false`. This prevents configured lifecycle/notification commands and delegation from becoming an implicit host-execution path; these settings are documented in the [configuration reference](https://learn.chatgpt.com/docs/config-file/config-reference).

## Managed subscription authentication

Use `account/login/start` with `{type:"chatgpt"}`. Keep that app-server alive through browser callback and `account/login/completed`. The admin process retains pending login state; cancel uses `account/login/cancel` and logout uses `account/logout`. Login URLs are accepted only over HTTPS on official OpenAI/ChatGPT domains. The adapter never reads credential storage and never extracts or forwards OAuth tokens. See [app-server authentication](https://learn.chatgpt.com/docs/app-server) and [official authentication documentation](https://learn.chatgpt.com/docs/auth).

CLI overrides enforce `model_provider="openai"` and `forced_login_method="chatgpt"`. `account/read` must actually report `type:"chatgpt"` before any turn; API-key accounts are not subscription-authenticated. OpenAI API environment credentials/base-URL overrides are removed from the subprocess environment. `Snapshot()` returns a cloned cached account/catalog view without process starts or RPCs; initial state has no `CheckedAt` timestamp and is explicitly unknown. `Refresh(ctx)` is an explicit operation that reloads an idle admin process, reads the account, and fetches the catalog. It preserves a pending browser flow's process. Login completion/account notifications update the snapshot; process exit clears dead pending links. Authentication failures remain visible until another auth action; transient transport errors clear after a successful refresh. This lets external `codex login` be picked up explicitly without reading credential files. Official CLI login caching is shared with other Codex clients, per [login caching](https://learn.chatgpt.com/docs/auth#login-caching).

Integration caveat: authentication in another shell must use the same HOME/CODEX_HOME and credential-store environment as the router. A pending in-router browser flow remains authoritative until completed or canceled. Login uses the official local callback listener; remote/headless installations must make that callback reachable or perform `codex login` externally, then refresh. No real login or inference was initiated while implementing this driver.

## Models, usage, and compatibility

`model/list` is paginated (`data`, `nextCursor`); expose actual `model`, `displayName`, `isDefault`, supported reasoning efforts and input modalities. Resolve requested `default` against the observed default at execution. Do not invent context limits, pricing, or model availability. See [model listing](https://learn.chatgpt.com/docs/app-server#list-models-modellist).

Agent text is streamed through `item/agentMessage/delta`. Token accounting uses `thread/tokenUsage/updated.tokenUsage.last`, not cumulative thread totals. Input tokens include cached input, so normalized uncached input is `inputTokens-cachedInputTokens`; missing usage stays unknown. Tool calls are returned to the client while the live server request remains unanswered. Text-only normalized message content is currently accepted; unsupported multimodal content fails explicitly rather than being discarded. Multiple server tool requests are naturally surfaced one at a time as the ongoing turn resumes.

System and developer message text is supplied through native `thread/start.developerInstructions`, not demoted into user content. `reasoning_effort` maps to `turn/start.effort`: in the 0.163.0 generated schema `ReasoningEffort` is a non-empty model-advertised string, not a hard-coded enum. Explicit effort changes during a pending tool turn are rejected. Unsupported explicit generation controls and `tool_choice` other than `"auto"` fail clearly rather than being silently ignored.

Rejected explicit controls: `temperature`, `top_p`, `max_tokens`, `max_completion_tokens`, `stop`, `seed`, `frequency_penalty`, `presence_penalty`, `response_format`, `parallel_tool_calls`, `logprobs`, `top_logprobs`, `n`, `logit_bias`, `prediction`, `modalities`, `audio`, and `service_tier`. Codex aliases used by omp must omit default API token caps (for example with omp's `omitMaxOutputTokens` override), because app-server has no equivalent per-request cap. `stream` and `stream_options` remain accepted transport fields.

The strict top-level allowlist is `model`, `messages`, `tools`, `reasoning_effort`, `tool_choice`, `stream`, and `stream_options`; other explicit fields also fail rather than being silently ignored. Unsupported content/control/tool-shape and client-history errors wrap exported `codex.ErrUnsupportedRequest`, allowing the HTTP adapter to return a client error before committing output instead of reporting a provider failure. This Codex adapter is OpenAI Chat-only; other upstreams' protocol support is unchanged.

The experimental dynamic-tool and environment fields make the installed CLI version a compatibility boundary. A CLI that rejects the safe thread configuration must fail closed; do not remove the restrictions to make inference work.

## Regression seam

`internal/codex/manager_test.go` exercises the public Manager API through a fake subprocess implementing authentic JSONL initialize/account/model/thread/turn and bidirectional tool RPC shapes. It checks text streaming, same-turn tool continuation, normalized last-turn usage, subscription status/catalog, and unmatched tool-result rejection. These regressions and the HTTP integration suite passed under `go test -race ./...`; `go vet ./...` also passed.

Additional public Manager subprocess regressions cover queued cancellation, active-capacity protection, same-key recovery after sign-in, immediate login completion before its response, persistent browser-flow errors across admin restarts, native developer instructions/effort, unsupported tool choice, and cancellation of blocked pipe writes.

The integration owner reported a successful real 0.163.0 `initialize` and safe `thread/start` smoke using the command restrictions, empty environments, tagged dynamic tools, read-only sandbox, explicit approval reviewer/policy, disabled shell/image/web/MCP/apps/agents, ephemeral state, and a temporary working directory. **No `turn/start`, inference, or login was performed** in that smoke. This validates configuration acceptance, not authenticated inference or model behavior.

The integrated console was then exercised against the real installed CLI: signed-out account status, model catalog, managed browser-login start, and cancellation all worked. No account sign-in was completed and no real model completion was attempted. Live HTTP requests with explicit token caps returned `400 unsupported_request`. A real omp process with read/bash tools sent a request to a controlled HTTP fixture; its fields matched the strict adapter allowlist after `omitMaxOutputTokens` and `compat.supportsStore: false` were configured. `omp models my-router` discovered the eight configured OpenAI/Codex aliases alongside the existing five aliases.
